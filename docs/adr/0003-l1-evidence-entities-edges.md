# L1 stores evidence, entities and edges; one worker writes the edges

L1 holds three kinds of data, each stored one way. **Evidence** is what a source recorded (transcript records, git observations, CLI captures, PR snapshots, GitHub API payloads): immutable rows, replaced only by a new generation. **Entities** are things with a current state (a pull request, a commit, a CI run attempt): one full row per version. **Edges** are relationships between them (a run created a commit, pushed it, named a PR; a commit is in a PR; a CI run ran on a commit): one row per relationship that names its `relation`, the `basis` it came from and the evidence row that witnesses it, written by a single reconciliation worker and readable in both directions. Inferences, such as a commit whose committer time falls inside a run, are **candidates**: stored apart, labelled, never part of L1. Everything analysis reads is in ClickHouse; Postgres keeps the control plane.

We chose this because resolving relationships at query time made `find source=git` reconstruct the same links on every call, from abbreviated SHAs, branch names and coverage rules, which took five review rounds to make correct, could not answer the reverse question (which runs touched this pull request) without scanning sessions, and merged ClickHouse and Postgres rows into one page, where most of its paging defects came from. DevLake, PostHog and Langfuse converged on the same split: immutable facts, versioned state, and relationships materialized when either side changes, with queries that only read.

## Considered Options

- Keep resolving at query time and add a reverse index: rejected; every query repeats the resolution, and its rules live in the query path instead of beside the data they produced.
- One ClickHouse materialized view joining transcript evidence to GitHub tables: rejected; a view fires only on inserts into its source table, so GitHub data that arrives later never updates the link.
- Attribute commits to runs by committer time: rejected for L1. Git lets callers set committer dates and a commit does not record its branch; Git AI forbids timestamp ownership for the same reason. Time matches are candidates.
- Typed edge tables per relationship (run → commit, commit → PR, …): deferred. One generic edge table gives one write path and one way for `find` to follow links; a relationship is split into its own table only when its volume requires it.
- Evidence stays in Postgres where it is captured: rejected for analysis reads. Postgres remains the source of truth for capture and upload protocols and publishes immutable copies to ClickHouse, as the repository evidence index already does.

## Consequences

- Each edge row carries `relation` (`commit_created`, `commit_pushed`, `commit_captured`, `sha_mentioned`, `pr_named`, `pr_branch_head`, `pr_listed`, `commit_in_pr`, `ci_on_sha`, `ci_for_pr`, …), `basis` (`transcript`, `capture`, `hook`, `github`), the witness `evidence_id`, `resolver_version`, `revision` and `is_active`. Creating a commit, pushing it, capturing it as HEAD and mentioning it are different relations; nothing is reduced to "produced". Evidence that belongs to no run (snapshots, captures, session metadata) is an edge from the session, never assigned to a run by time.
- Relationships are many-to-many. A run that committed is not proof that it wrote the code; line provenance is a later, separate kind of evidence.
- The worker rebuilds a scope (a session generation, a repository's pull requests or CI runs) whenever an input changes, writes new revisions and retractions, and advances a watermark. Its queue, claims and watermarks are Postgres rows (`SKIP LOCKED`); its output is ClickHouse. Rebuilds are deterministic, so a retry or duplicate write is harmless. It is fenced by the purge tombstones like the other derived workers.
- Materialized views only reshape a single source, such as the reverse copy of the edge table ordered by target. They never join two sources and never parse transcript content.
- `find` follows edges and joins the current state of a bounded set of entities; it does not resolve abbreviations, match branches or decide completeness. Completeness is a property of an edge source's coverage watermark.
- New sessions get exact ownership from capture: the CLI records the ref positions before and the full object IDs after each git command an agent runs (Claude Code tool hooks), with worktree and process identity; Codex gets per-turn checkpoints. Old sessions keep the transcript and capture evidence they have; elsewhere the answer is unknown or a labelled candidate, and trends compare periods on the same `basis`.
- ClickHouse never holds control state that needs uniqueness or claims, and Postgres never holds data analysis scans. The spec is `docs/l1-literal-schema.md`.
