# Retro

A retro, or "how do I improve my agents": follow these steps in place of steps 2-6 of the playbook in SKILL.md.

1. **Digest.** `patterns action=digest` with the `repository`, `from` and `to` (default the last 30 days). It is one block of every retro number, each with its definition: start dirs and instruction files loaded at start, failures (its top patterns included), context and cost, time sinks, tool routing, checks and CI, the person, agents, a severity lane and what nothing explains. It is a map of what is measured, not the answer: the most important problem may be outside it. Call `patterns action=list kind=<kind>` only when you need more rows of one kind than the digest shows.
2. **Choose 5-8 problems** that span the dimensions with signal, ranked by sessions × minutes. Done when every dimension with signal has been weighed and each problem names its digest row. Report every severity-lane hit (destructive commands, production writes, secrets, lost work) whatever its count. A row that says "not recorded" is unknown, not zero.
3. **Open pass, required, small budget.** Read the Unexplained examples and about 15 genuine prompts sampled across the window (`sql` over `prompts` with `at >= '<from>' AND genuine = 1 AND agent_id = ''`, `ORDER BY cityHash64(session_id, record_idx, '<any word>') LIMIT 15`, since sql has no `rand()`; or the pulled records). Run at least one `search`, `sql` or `opaline count` on something the digest did not show. Report it under its own heading, "Outside the digest", even when that says "nothing new".
4. **Why.** Read 1-2 example runs per problem: `run id=<session#turn>` with the row's `session#turn` (or `session:agent#turn`) as it is, `read`, or `patterns action=drill id=…`. Done when each problem has a cause you saw in a run.
5. **Numbers.** Every number in the report is either quoted from the digest or patterns with its definition, or computed by you and checked with one `opaline count` (one `sql` where there is no shell). Write the definition next to the number in a few words, e.g. "(main-stream error results containing 'no matches found')". Cite a session by the `session_id` field of the row you read; an id inside prompt or output text (such as a URL) points to another session.
6. **Write** the report: the problems, "Outside the digest", and each fix as a diff against the repository, of the kind `fix_type` names: AGENTS.md or CLAUDE.md, a doc or skill, a tool's description or schema, a script in package.json, a comment at the file's top, a hook or an allowlist entry. Something the person said in prose gets an instruction, a doc or a skill. Use `fix_hint` for the target; quote the setup text the runs received where it matters. Show the diff; change files only when the user asks. Then `save_answer` (as in "Save and answer" in `SKILL.md`) with the health block at the end of `finalAnswer`, the block the report page and the repository Health tab read: a fence opening with three backticks and `opaline-health` and closing with three backticks, both at the start of a line with no indentation, one JSON object per line, nothing else in the block, keys exactly as below and no others:
   ```opaline-health
   {"type":"Summary","headline":"<the state of the repository's agent setup in one sentence, no numbers>"}
   {"type":"Signal","id":"<pattern id>","area":"<area>","label":"<the signature in plain words>","status":"<pass|warn|fail>","source":"session","rule":"pass: runs with it per 100 runs fall after the last instruction or skill change","observed":"<count> in <runs> runs of <sessions> sessions, <minutes> min, <from>..<to>; verify <before> -> <after> per 100 runs (<verdict>)","evidence":"<one sentence naming the example run you read and what it shows>","runId":"<that run's run_id>"}
   {"type":"Action","rank":1,"title":"<the fix in a few words>","why":"<why the pattern happens, from the runs you read>","area":"<area>","impact":"<high|medium|low>","effort":"<minutes|hour|day>","signals":["<pattern id>"],"fixes":[{"path":"<file>","before":"<a short unique excerpt of the file as it is, empty for a new file>","after":"<the same excerpt with the change>"}]}
   {"type":"Quirk","title":"<an odd or repeated habit of the agents>","note":"<what and where>","runId":"<run_id>"}
   {"type":"Readme","path":"README.md","found":true,"verdict":"<helps|partial|stale|missing>","summary":"<what it gives the runs>"}
   ```
   One Summary line; one Signal per pattern you picked; one Action per fix, rank 1 first, each naming the Signals it fixes, with `fixes` holding the diff from step 6 as before/after text, one entry per file (up to 6). `area` follows `fix_type`: `install_or_agents_md` environment; `script_and_pointer` and `align_ci_check` build; `navigation_pointer`, `agents_md_rule`, `instruction`, `doc` and `comment_at_entry` documentation; `stop_hook` testing; `allowlist` security; `tool_schema`, `pretooluse_hook` and `skill` agent; a theme takes the area of the fix you chose. `status` follows `patterns action=verify`: `improved` pass, `unchanged` or `no_change_yet` warn, `worse` fail; with `no_change_yet` write "verify once the fix merges" in place of the before/after numbers. `impact` is high for the pattern that costs the most minutes, low for one under a tenth of its minutes, medium otherwise. Quirk lines (0-3) are optional; write a Readme line only when you read the README in the runs or the repository. Labels at most 120 characters, observed and rule 200, evidence 300, why 400; cite runs by run_id exactly as `run` or sql returned them.
7. Offer to save each pattern that should not come back as a check (`checks action=test`, then `action=create`), and to rerun `patterns action=verify id=<id> since=<the day the fix merged>` later.

## Budget

A retro takes about 20-30 tool calls. Spend them on reading runs and prompts.
- A digest or patterns row answers its own question: quote it with its definition.
- `opaline pull` only when a number you need is in no digest or patterns row, at most once, then `opaline count` over the pull. One `opaline count` checks one number; write a script only for a definition `count` cannot express.
- Keep every command's printed output under about 15,000 characters: print counts and a few example lines, and write longer output to a file you read in parts. Larger output lands in a file you read again, at the cost of a call and its tokens twice.
- One diff per change in the report, and no more than the report needs.
